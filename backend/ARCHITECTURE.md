# IOTA ML Backend Architecture

## Purpose

IOTA ML is a self-hosted no-code machine-learning and scientific data-processing platform. The backend preserves the existing React frontend contract while providing one FastAPI application, one SQLAlchemy metadata tree, one workflow runtime, one node registry, and one storage abstraction.

## Runtime services

```text
React frontend
      |
      | REST/JSON + authenticated artifact downloads
      v
FastAPI API
      |---------------- PostgreSQL (durable source of truth)
      |---------------- Redis (wake-up, throttling, transient coordination)
      |---------------- Local storage or MinIO (immutable object data)
      `---------------- Reliable worker processes
```

PostgreSQL owns users, projects, datasets, workflow revisions, reusable components, runs, run attempts, run events, node executions, artifacts, lineage, quota reservations, and cache metadata. Redis is never the authoritative run queue. Uploaded and generated bytes are stored through the canonical storage interface.

## Package boundaries

- `app/core/`: configuration, database/session ownership, security, errors, response envelopes, request context, logging, and OpenAPI composition.
- `app/domains/`: HTTP routes, schemas, repositories, services, and ORM models owned by each business domain.
- `app/infrastructure/storage/`: local and MinIO implementations behind one interface.
- `app/infrastructure/queue/`: durable PostgreSQL claim/state logic and optional Redis notifications.
- `app/infrastructure/observability/`: metrics and operational instrumentation.
- `app/workflow/`: compatibility normalization, graph operations, static validation, planning, execution, and caching.
- `app/nodes/`: typed node contracts, registry, catalog generation, and implementations.
- `app/workers/`: worker lifecycle, child execution, signal handling, and maintenance jobs.

The removed legacy parallel locations are `app/api/`, `app/models.py`, `app/database.py`, `app/storage/`, and `app/services/workflow_executor.py`.

## Domain ownership

| Domain | Owned records and responsibilities |
|---|---|
| `auth` | Users, login, signed bearer tokens, profile data and profile images |
| `projects` | Project ownership and project summaries |
| `datasets` | Dataset metadata, ID-column metadata, bounded previews and deletion |
| `workflows` | Saved graphs, revisions, autosave, versions and restore |
| `components` | Reusable component definitions and immutable component versions |
| `runs` | Run creation, idempotency, status, attempts, progress, retry and cancellation |
| `artifacts` | Object metadata, lifecycle, lineage, quota reservations, node execution records and cache metadata |
| `nodes` | Built-in catalog and owner-scoped custom-node metadata |
| `assistant` | Optional assistant endpoint, enabled only when configured |

Routes handle HTTP details only. Services own use-case and transaction boundaries. Repositories contain SQLAlchemy queries and do not commit implicitly unless their method contract explicitly says so.

## Request flow

1. `ApiEnvelopeMiddleware` accepts or generates `X-Request-ID`.
2. Authentication resolves the bearer-token subject against the database.
3. The route validates bounded Pydantic input and calls a domain service.
4. The service verifies ownership and coordinates repositories and infrastructure.
5. The service commits or rolls back one explicit transaction.
6. The response is serialized as the frontend-compatible success or error envelope.
7. Structured logs and metrics include the request ID and available domain identifiers.

Success envelope:

```json
{"success": true, "data": {}, "meta": {}, "request_id": "..."}
```

Error envelope:

```json
{"success": false, "error": {"code": "...", "message": "...", "details": {}}, "request_id": "..."}
```

## Database foundation

`app/core/database.py` is the only engine/session composition module. It owns:

- One `DeclarativeBase`.
- One configurable engine factory.
- One `SessionLocal` factory.
- One FastAPI `get_db()` dependency.
- Pool pre-ping, bounded pool size/overflow, timeout and recycle settings.
- SQLite-compatible test overrides.

`app/core/model_registry.py` imports every domain model for Alembic without reintroducing model ownership duplication. All timestamps use the shared UTC helper.

## Run creation and queue flow

Run creation is transactional:

1. Validate workflow/project/dataset ownership.
2. Validate the requested workflow revision and execution target.
3. Store an immutable graph snapshot on the run.
4. Enforce owner/project active-run limits and idempotency.
5. Insert a `queued` run and commit.
6. Publish a best-effort Redis wake-up after commit.

A Redis failure cannot lose the run because PostgreSQL remains authoritative.

Workers claim eligible runs with `FOR UPDATE SKIP LOCKED`, a conditional owner update, an attempt number, and heartbeat metadata. Supported final state rules use the states needed by the existing frontend and reliability layer: `queued`, `claimed`, `running`, `succeeded`, `failed`, `cancel_requested`, `cancelled`, `retry_wait`, and `dead_letter`.

Retry classification separates deterministic validation/node errors from transient database, storage, and coordination failures. Completion checks the active worker owner so a stale worker cannot overwrite a recovered run.

## Worker/child boundary

The parent worker owns database persistence. A child process receives a bounded immutable run snapshot and writes bounded progress/result files under the runtime directory. It does not initialize the application database engine for ordinary node execution. The worker:

- Stops claiming jobs on `SIGTERM` or `SIGINT`.
- Signals active child cancellation.
- Waits a configured grace period.
- Terminates non-responsive children.
- Leaves interrupted work in a recoverable state.
- Bounds stdout, stderr, result and progress data.
- Cleans expired runtime directories through maintenance jobs.

Custom Python execution is disabled by default. When explicitly enabled for a trusted installation, the child receives a sanitized environment and CPU, memory, file, descriptor, process and timeout limits. This is defense-in-depth, not a secure hostile multi-tenant sandbox.

## Canonical workflow pipeline

```text
Saved graph
  -> compatibility normalization
  -> canonical graph model
  -> static validation
  -> execution plan
  -> canonical scheduler/runtime
  -> artifact publication
  -> run finalization
```

The compatibility normalizer maps historical node IDs and graph field variants to the canonical model. Both historical and current graphs then use the same validator, planner, scheduler, cache, artifact publication and error contract.

Static validation checks duplicate IDs, cycles, missing nodes, invalid handles, required connections and parameters, parameter types/options, incompatible port types, multi-edge violations, missing columns/ID metadata when known, and output-port selection.

Selected-node execution computes the complete upstream dependency closure and executes only that subgraph. Full execution uses deterministic topological ordering. Downstream nodes are skipped after an upstream terminal failure.

## Node contracts and registry

Every registered node supplies a stable node ID, display metadata, implementation version, parameter schema, input/output ports, execution implementation, cacheability and determinism metadata. The registry contains 64 executable definitions and 57 compatibility aliases for historical saved graphs.

`python -m app.nodes.catalog.generate --check` validates and compares the generated frontend-facing JSON catalog. Generation fails for duplicate IDs or aliases, missing versions, invalid/default-mismatched parameters, duplicate ports, or unimportable implementations.

## Dataframe and ID-column contract

Tabular boundaries carry a canonical dataframe contract containing columns, dtypes, row count when known, ID-column metadata, uniqueness state, source artifact, schema fingerprint, aliases and lineage. The ID column:

- Propagates by default.
- Is excluded from numeric calculations unless a node explicitly supports it.
- Is placed first in exports by default.
- Participates in cache fingerprints.
- Produces a structured duplicate-ID error when uniqueness is required.
- Can be changed only by an explicit node contract.

Interactive edits create a new artifact revision; immutable upstream artifacts are not silently changed.

## Artifact lifecycle

Canonical states are `pending`, `uploading`, `available`, `failed`, `delete_pending`, and `deleted`.

Upload flow:

1. Validate owner, project, filename, size and content policy.
2. Create a pending artifact and reserve quota transactionally.
3. Stream to a UUID-scoped temporary object key while hashing SHA-256.
4. Verify stored size/checksum metadata.
5. Finalize to an immutable key.
6. Mark the artifact available and create dataset/run/node/cache/lineage links.
7. Release quota reservation.

Failures mark the artifact failed, release reservation, and attempt temporary cleanup. A dataset cannot point to an unavailable artifact.

Deletion first marks `delete_pending`, evaluates pinning/lineage/cache references, removes eligible object data, then marks `deleted` while retaining audit metadata.

Reconciliation is idempotent, batch-bounded and available through `python -m app.workers.maintenance artifacts`. It identifies stale pending uploads, missing objects, broken cache references, failed temporary uploads, delete-pending records, expired artifacts and optional checksum mismatches.

## Cache flow

Cache keys use canonical JSON and include node stable ID/version, normalized parameters, input checksums, port mapping, ID-column metadata, dataframe schema fingerprint, component version and output-affecting execution mode. Entries reference immutable `available` artifacts and are scoped by owner/project. Missing/deleted artifacts invalidate entries. Cache hits still create node-execution records.

## Observability and health

Structured JSON logs include request, user, project, workflow, revision, run, attempt, node, worker and artifact context when available. Secrets and large fields are redacted or bounded.

- `/health/live`: process liveness only.
- `/health/ready`: bounded PostgreSQL and storage checks; Redis only when configured as required.
- `/metrics`: Prometheus-compatible counters/gauges when enabled.

Operational metrics cover API requests/errors, queue depth/age, run/node duration, retries, dead letters, worker heartbeat, storage failures, reconciliation findings and cache usage.

## Maintenance jobs

```bash
python -m app.workers.maintenance artifacts --dry-run
python -m app.workers.maintenance stale-runs
python -m app.workers.maintenance cache --dry-run
python -m app.workers.maintenance logs --dry-run
python -m app.workers.maintenance runtime --dry-run
python -m app.workers.maintenance usage
python -m app.workers.maintenance dead-letter
python -m app.workers.maintenance all --dry-run
```

Jobs use advisory locks on PostgreSQL, bounded queries, short transactions, structured summaries and dry-run support for destructive work.

## Connection budget

With the example defaults:

```text
2 API processes x (5 pool + 5 overflow) = 20 maximum
1 worker parent x (5 pool + 5 overflow) = 10 maximum
maintenance/migration/admin reserve       = 10 minimum
recommended PostgreSQL max_connections    >= 40
```

Child execution processes do not open general-purpose database pools. Adjust `DATABASE_POOL_SIZE`, `DATABASE_MAX_OVERFLOW`, API worker count, and worker replicas together. PgBouncer is a future scaling option, not a dependency of this release.
